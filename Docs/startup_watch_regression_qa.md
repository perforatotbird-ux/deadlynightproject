# Исправление зависания управления после обновления часов

## Воспроизведение и границы диагноза

На версии `e370a9e` удаление только импортированного `.scn` модели `left_arm_round_watch.glb` воспроизводит: ошибка `preload` в `WatchArm.gd`, прерывание `_ready` контроллера до создания HUD/меню и ошибки обращения к отсутствующему HUD каждый физический кадр до перемещения игрока. Это подтверждённый сценарий с симптомами жалобы; без логов компьютера игрока нельзя утверждать, что именно так повреждён его checkout. Полный чистый checkout той же версии с успешным импортом запускается.

## Исправление

- Контроллер сначала полностью инициализирует ввод, HUD, инвентарь и паузу; часы подключаются последними через runtime load, без жёсткой compile-time зависимости.
- Отсутствующая/неверная модель часов отключает только визуал и сообщает о восстановлении ассетов. T не обращается к несуществующему экземпляру.
- `run.bat` проверяет LFS-указатели во всех `assets/` и `data/`, выполняет импорт и отдельный `LaunchCheck.gd`. При ошибке выводит диагностику вместо запуска неуправляемого мира. Логи находятся в `logs/`.
- Пользовательские сохранения и настройки не изменяются.

## Проверки

Godot 4.7.2, Linux, изолированные пользовательские профили:

- Инкрементальный импорт и LaunchCheck: успешно; 70 production-скриптов компилируются.
- `test_gameplay_startup.gd`: 14 PASS, 0 FAIL в настоящем `MapViewer.tscn`, без отключения физики игрока. Движение, Tab, M, Esc, возобновление, T, динамические цифры и повторное движение после меню.
- Та же сцена с намеренно убранным импортированным `.scn` часов: 14 PASS, 0 FAIL. Часы недоступны, но ввод, меню, движение и инструмент работают. Ожидаемая диагностика загрузчика модели остаётся в логе; нет прежних ошибок скрипта и null-HUD.
- LaunchCheck на повреждённом кэше завершает процесс кодом 1, на исправном — 0.
- 16 существующих наборов: watch, part2, steps_and_falls, exploration_map, exploration_map_world, calories, vegetation, health_dev, first_night, backpack_tabs_actions, inventory_redesign, forest_bed, survival_batches, atmosphere, atmosphere_integration, survival_rework — 0 FAIL. В first_night и atmosphere_integration движок также сообщает о ресурсах, оставшихся при завершении процесса; это не оценивалось как исправленная часть данной задачи.

Windows `cmd.exe` и целевой GPU игрока в этом окружении недоступны: непосредственно выполнение `.bat` на Windows не проверено. Результаты проверки движка не заменяют лог с компьютера игрока.

## Восстановление checkout игрока

```bat
git pull
git lfs install
git lfs pull
run.bat
```

Если ошибка остаётся, нужны `logs/DeadlyNight-import.log`, `logs/DeadlyNight-startup.log`, `logs/DeadlyNight-runtime.log` (последний создаётся только после успешной предпроверки). При подтверждённо повреждённом кэше закрыть Godot, переименовать `.godot` в свободное резервное имя и повторить `run.bat`. Не удалять AppData/сохранения.

Дополнительный оконный прогон X11/Compatibility не завершён: процесс был принудительно завершён с кодом 137 после создания леса, до проверок ввода. Успешный GPU/оконный прогон в результаты этой задачи не включён; подтверждённые 14/14 выше относятся к headless-интеграции реальной сцены.
